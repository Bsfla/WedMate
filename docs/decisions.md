# 결정 로그

> **왜 그렇게 정했는가**를 남기는 곳. 새 항목은 **맨 아래에 덧붙이고**, 기존 항목은 고치지 않는다.
> 결정이 뒤집히면 기존 항목에 `→ D-00N에서 번복` 한 줄만 달고 새 항목을 쓴다.
>
> 코드를 보면 알 수 있는 것(무엇을 했는가)은 여기 쓰지 않는다. 코드를 봐도 모르는 것(왜)만 쓴다.

## 확정

### D-001 · 커플 2인 공유 스페이스 (2026-07-29)
개인 가계부가 아니라 예랑/예신이 각자 로그인해 같은 데이터를 보는 구조로 간다.
결혼 준비 지출의 실제 니즈가 "누가 얼마를 냈고 어떻게 정산하나"이기 때문이다.
→ 모든 테이블에 `couple_id` + RLS, `expenses`/`budgets`/`guests`는 Realtime 구독.

### D-002 · 결제수단에서 payer를 분리 (2026-07-29)
원본 시트는 `예신 현금`·`예랑 카드`처럼 **결제자를 결제수단 문자열에 인코딩**해 두었다.
이걸 그대로 옮기면 분담 정산 집계를 문자열 파싱으로 해야 한다.
→ `payer`(groom/bride/joint)와 `method`(cash/card/voucher/account)를 별도 컬럼으로 정규화.

### D-003 · 계약금/중도금/잔금을 enum으로 승격 (2026-07-29)
시트에서는 메모 텍스트로만 존재해 "잔금 미납 항목"을 뽑을 수 없었다.
→ `payment_stage` enum. 홈 화면의 잔금 미납 경고가 여기서 나온다.

### D-004 · 일자 미입력 = 예상 지출 (2026-07-29)
시트의 규칙(일을 비우면 빨간색으로 표시되고 월별 예상금액에 잡힘)을 그대로 보존한다.
→ `spent_day IS NULL`이면 `is_estimated`. **확정 지출 합계·소진율에는 넣지 않고** 월별 타임라인의
별도 계열로만 반영한다. 홈의 대표 숫자는 확정, 예상은 보조.

### D-005 · 배분 초과를 경고한다 (시트에 없던 개선분) (2026-07-29)
시트는 결혼식 대분류 배분 13,000,000 vs 소분류 합 13,380,000의 불일치를 경고하지 않는다.
사용자가 모르고 지나칠 수 있는 실제 결함이다.
→ 앱은 `Σ(하위 소분류 예산) > allocation`이면 예산 화면에 경고 배너를 띄운다.

### D-006 · 색만으로 정보를 전달하지 않는다 (2026-07-29)
구분해야 할 축이 세 개(확정/예상 · 결제자 3종 · 대분류 4종)라 색에만 기대면 색각 이상 사용자에게 무너진다.
→ 확정은 채운 막대 / 예상은 **점선 + 45° 사선 패턴 + "예상" 배지**, 결제자와 대분류는 색과 함께
**텍스트 라벨을 항상 병기**. 그레이스케일로 렌더해도 모든 구분이 살아남아야 한다.

### D-007 · 대비 미달 토큰은 텍스트로 쓰지 않는다 (2026-07-29)
구현 전에 대비비를 계산해 보니 세 토큰이 흰 배경에서 WCAG AA(4.5:1)에 못 미쳤다 —
`--warning #D97706` 3.18:1, `--success #059669` 3.77:1, `--payer-groom #0EA5E9` 2.77:1.
→ 이들은 **면·테두리·아이콘 전용**으로 못 박고, 텍스트가 필요한 자리에는 `-strong` 토큰
(`#B45309` 5.02:1 / `#047857` 5.48:1 / `#0369A1` 5.93:1)을 쓴다.
`--primary #E11D48`은 4.70:1로 통과하므로 본문에도 쓸 수 있다.

### D-008 · 진행률 바에 Recharts를 쓰지 않는다 (2026-07-29)
소진율 바·게이지·진행률은 전부 `div` + `role="progressbar"`로 만든다 —
더 가볍고, 스크린리더가 값을 읽고, 다크 모드 대응이 자동이다.
→ **Recharts는 월별 타임라인 하나에만** 쓴다.

### D-009 · 바텀시트를 shadcn drawer로 만들지 않는다 (2026-07-29)
현재 shadcn drawer는 Base UI 기반이라, `-b radix`로 init한 이 프로젝트에 두 번째 프리미티브
라이브러리를 끌고 들어온다.
→ 이미 설치된 `radix-ui`의 Dialog 위에 직접 만든다. 새 의존성 0개, 44px·safe-area·최대높이를 통제.

### D-010 · 화면은 fixtures 선택자 함수만 호출한다 (2026-07-29)
목업을 화면 곳곳에 흩어 두면 P2~P5에서 화면 코드를 전부 다시 만져야 한다.
→ 화면은 `getMockHome()` 같은 **함수 하나**만 부르고, P2~P5는 그 함수 본문만 Supabase 쿼리로
갈아끼운다. 도메인 어휘는 `lib/domain.ts`에 따로 둬서 목업이 사라져도 남는다.

### D-011 · 목업 집계는 원시 배열에서 파생시킨다 (2026-07-29)
합계를 손으로 적어 두면 항목을 하나 고칠 때마다 숫자가 어긋난다.
→ `fixtures.ts`는 예산·지출·하객 원시 배열만 갖고 총액·진행률·정산·타임라인을 전부 계산한다.
덕분에 `?fixture=sheet`가 시트 실측치를 자동으로 재현한다.

### D-012 · 사선 패턴 색에 color-mix()를 쓰지 않는다 (2026-07-29)
Tailwind v4는 `color-mix()`를 쓴 선언마다 `var(--원색)` 폴백을 자동으로 깐다.
테두리·배경에서는 "약간 진해지는" 정도라 무해하지만, **그라디언트 색상 정지점에 쓰면
4% 틴트가 100% 불투명 줄무늬로 뒤집힌다.**
→ `--estimate-tint` / `--estimate-stripe`에 미리 섞은 값을 넣고 유틸은 그 변수만 참조한다.

### D-013 · D-day 기준일을 고정한다 (목업 한정) (2026-07-29)
`new Date()`로 계산하면 정적 프리렌더 시점에 얼어붙어 배포 뒤 값이 어긋난다.
→ 목업 단계에서는 `MOCK_TODAY`를 고정해 결정적으로 만든다. **P6에서 걷어낸다.**

### D-014 · 로그인은 이메일 매직링크 하나로 시작 (2026-07-29) → **D-033에서 번복**
기획안은 "카카오 OAuth + 이메일 매직링크"였다. 카카오는 개발자 앱 등록 · 리다이렉트 URI 설정 ·
심사가 선행되어야 해서 **P1 전체를 막는다**.
→ 매직링크만으로 P1을 끝내고 카카오는 2차 백로그로 미룬다. `couple_members`가 `user_id`만
참조하므로 나중에 붙여도 스키마 변경이 없다.

### D-015 · 카테고리를 커플 소유로 복사 시드한다 (2026-07-29)
전역 템플릿을 참조하게 하면 커플이 항목을 고칠 수 없다. 스몰웨딩이라 폐백이 없거나 반대로
"본식 DVD"가 필요한 경우가 실제로 흔하다.
→ 스페이스 생성 시 기본 트리(대4/중11/소25)를 `couple_id` 소유로 **복사**한다.
대분류 4개만은 추가·삭제를 막는다 — 배분·차트 색·결산 구조가 4개에 묶여 있다.

### D-016 · 카테고리·결제수단은 삭제하지 않고 보관한다 (2026-07-29)
지출이 이미 참조 중인 카테고리를 지우면 과거 기록과 결산이 깨진다.
→ `is_archived` / `is_active`로 감춘다. 새 지출의 선택지에서는 빠지되 기존 기록에는 남는다.

### D-017 · 초대 코드는 RPC로만 사용한다 (2026-07-29)
참여하려는 사람은 **아직 멤버가 아니라서** 일반 RLS 정책으로는 `couple_invites`를 볼 수 없다.
정책을 느슨하게 풀면 코드 목록을 통째로 긁어갈 수 있다.
→ 테이블 직접 SELECT는 막고 `redeem_invite(code)` `SECURITY DEFINER` RPC 하나로만 연다.
코드는 6자리(혼동 문자 `0/O/1/I` 제외), 유효기간 7일, 1회용, 재발급 시 이전 코드 즉시 만료.

### D-018 · `couple_members` RLS는 SECURITY DEFINER 헬퍼로 푼다 (2026-07-29)
`couple_members`에 `couple_id IN (SELECT couple_id FROM couple_members WHERE ...)`를 그대로 걸면
**자기 참조 무한 재귀**가 난다 (Postgres가 정책 평가 중 같은 정책을 다시 부른다).
→ `current_couple_id()` `SECURITY DEFINER` 함수를 만들어 정책에서 호출한다.

### D-019 · 설정 화면은 자동 저장, 온보딩은 명시적 저장 (2026-07-29)
설정은 한 항목씩 고치는 화면이라 매번 저장 버튼을 누르게 하면 번거롭다.
반면 온보딩·바텀시트는 여러 필드를 한 벌로 채우는 화면이라 명시적 커밋 지점이 필요하다.
→ `/settings/*`는 자동 저장, `/onboarding/*`과 바텀시트는 저장 버튼.

### D-020 · 카테고리 순서변경은 ↑↓ 버튼으로 한다 (2026-07-29)
드래그는 세로 스크롤과 충돌하고(모바일에서 특히), 접근성 처리가 무겁다.
→ 행 우측의 ↑↓ 버튼. 44px 터치 타깃을 지키기 쉽고 스크린리더로도 조작 가능하다.

### D-022 · shadcn 프리미티브는 P1에서 받는다 (2026-07-29) — O-003 해소
PD 단계에서는 쓰이는 곳이 없어 받지 않았다. P1이 앱의 첫 폼 화면이므로 여기서 받는다.
→ `input` `label` `select` `checkbox` `switch` `separator` `skeleton`.
**받은 직후 반드시** nova 프리셋의 데스크톱 밀도(h-8 등)를 48px/16px 규격으로 손보고,
각 파일 상단에 shadcn 덮어쓰기 경고 주석을 남긴다 (`button.tsx`와 동일한 처리).

### D-021 · 3단 트리를 3단 들여쓰기로 그리지 않는다 (2026-07-29)
375px에서 세 단계를 들여쓰면 소분류 이름이 잘린다.
→ 대분류는 섹션 헤더, 중분류는 그룹 헤더, **소분류만 리스트 행**으로 한 단계(16px)만 들여쓴다.

### D-023 · 결제자에 '기타'(제3자)를 추가해 4종으로 간다 (2026-07-30) — O-005 해소
부모님 지원금은 한국 결혼 준비에서 흔하다. (b)안(예산 자체를 줄여 반영)은 **얼마를 지원받았는지가
기록에 남지 않아** 나중에 되짚을 수 없다. → O-005의 (a)안 채택.

`payer = groom | bride | joint | other`. 핵심은 **`joint`와 `other`가 다른 개념**이라는 점이다.

| | 돈의 출처 | 분담 정산 |
|---|---|---|
| `joint` 공동 | 커플 공동계좌 | 양쪽에 ½씩 귀속 |
| `other` 기타 | 부모님 등 제3자 | **전액 제외** |

- `SettlementView.total`은 이제 **커플 부담 합계**다(기타 제외). 결산 화면의 문구도
  "총 확정 지출"에서 "커플 부담 합계"로 바꿨다 — 이름과 값이 어긋나면 버그로 읽힌다.
- 기타는 `otherTotal`로 분담 정산 패널에 **별도 줄**("분담 정산에서 제외")로 표시한다.
  숨기면 총 확정 지출과 커플 부담 합계의 차이를 설명할 수 없다.
- 색은 `--payer-other` 바이올렛(`#8B5CF6`) — `--chart-5`(기타)와 같은 색으로 맞췄다.
  텍스트에는 `--payer-other-strong #6D28D9`(7.10:1)를 쓴다 (D-007과 같은 규칙).
- `payment_methods` 조합은 `결제자 4 × 수단 4 = 16`으로 늘어난다.

### D-024 · 사용자 이름은 `couple_members.display_name`에 복사한다 (2026-07-30)
Supabase는 `auth` 스키마를 PostgREST에 노출하지 않는다. 클라이언트가 얻을 수 있는 사용자 정보는
`auth.getUser()`로 조회하는 **자기 자신뿐**이라, `auth.users`를 조인해 **상대방 이름을 가져오는 설계는
아예 불가능**하다. 그런데 `/settings/invite`의 멤버 목록은 상대를 보여줘야 한다.
→ 참여 시점에 이름을 `couple_members.display_name`(NOT NULL)에 **복사**한다.
별도 `profiles` 테이블은 두지 않는다 — 사용자 1명이 커플 1개에만 속하므로 `couple_members`가 곧
프로필 자리다. 한 사람이 여러 스페이스를 갖게 되면 그때 분리한다.

### D-025 · 물리 설계 4원칙 — bigint · text+CHECK · View · RESTRICT (2026-07-31)
erd.md 0절의 검토 항목을 확정한 것이다. 넷 다 "나중에 바꾸기 쉬운 쪽"을 골랐다.

| | 정한 것 | 왜 |
|---|---|---|
| 금액 | `bigint` 원 단위 정수 | `numeric`은 원화에 과하고 느리다. `int`는 상한 21억이라 총예산·축의금 합계에서 아슬아슬하다 |
| enum | `text` + `CHECK (col IN (...))` | `CREATE TYPE ... AS ENUM`은 값 하나 추가에도 마이그레이션이 필요하고 되돌리기 어렵다. `payer`에 `other`를 넣은 일(D-023)이 또 생긴다 |
| 집계 | RPC 아닌 **View** | View는 RLS를 그대로 상속한다. 권한 로직을 두 번 쓰지 않고, 타입 생성도 따라온다. 인자가 필요하거나 쓰기를 하는 것만 RPC로 남긴다 |
| 카테고리 삭제 | `ON DELETE RESTRICT` | 보관 정책(D-016)과 짝이다. 지출이 참조 중인 카테고리는 DB가 삭제를 막고 화면은 `is_archived`로만 감춘다. 커플 자체가 지워질 때만 `CASCADE` |

**View에는 반드시 `WITH (security_invoker = on)`을 적는다.** 이건 기본값이 아니다 — 빠뜨리면
View가 소유자 권한으로 돌아 호출자의 RLS를 통과하고, 남의 커플 결산이 그대로 보인다.

### D-026 · `is_confirmed`를 뺀다 — 확정 여부는 `spent_day`만이 결정한다 (2026-07-31)
product.md에는 `is_confirmed`와 `is_estimated`가 둘 다 있었는데 `is_confirmed = NOT is_estimated`라
같은 사실을 두 번 저장하는 셈이었다. 둘이 어긋나는 순간 어느 쪽이 진실인지 알 방법이 없다.
→ `is_estimated bool GENERATED ALWAYS AS (spent_day IS NULL) STORED` 하나만 남긴다.
D-004의 시트 규칙이 그대로 DB 제약이 된다.

"등록했지만 아직 돈이 안 나갔다"는 **별도 상태**가 필요해지면 그때 `is_paid`라는 이름으로 새로
추가한다. 확정/예상과는 다른 축이므로 이 컬럼을 되살리는 형태여선 안 된다.

### D-027 · 대분류에 `major_key` 고정 키를 둔다 (2026-07-31)
`MAJORS`(lib/domain.ts)의 차트 색·결산 구조·최종 손익 계산이 전부 `wedding | honeymoon |
household | home` 네 키에 묶여 있다. 그런데 카테고리 이름은 사용자가 바꿀 수 있다.
"결혼식"을 "본식"으로 고치는 순간 이름으로 매칭하던 코드가 전부 끊긴다.
→ `categories.major_key`(대분류에만 NOT NULL, 값 4종 고정, `UNIQUE(couple_id, major_key)`).

쓸 수 있는 키가 없어 INSERT 자체가 실패한다. (삭제 금지는 여전히 앱 규칙이다 — 배분·지출이
걸려 있으면 RESTRICT가 막지만, 빈 대분류는 DB가 막지 않는다.)

### D-029 · 초대 코드 무효화는 `revoked_at`으로 한다 (2026-07-31)

만료된 코드도 `revoked_at`이 비어 있으면 인덱스를 계속 점유하기 때문이다.

### D-033 · 로그인을 이메일+비밀번호로 바꾼다 (2026-07-31) — D-014 번복
D-014는 "카카오 OAuth vs 매직링크"만 비교했다. **비밀번호가 후보에 없었다.**

매직링크를 구현하려다 두 가지가 걸렸다.

1. **기기 간 이동이 안 된다.** `@supabase/ssr` 기본값인 PKCE는 code verifier를 *요청을 보낸
   브라우저의 쿠키*에 둔다. PC에서 로그인을 누르고 폰으로 메일을 열면 실패한다 —
   예비부부가 각자 폰으로 쓰는 앱에서 이 경로는 예외가 아니다.
   (`token_hash` + `verifyOtp`로 우회 가능하지만 이메일 템플릿을 손으로 고쳐야 한다.)
2. **메일이 안 나간다.** Supabase 내장 SMTP는 테스트용이라 발송량이 매우 적고 수신자도 제한된다.
   P1 완료 판정의 "계정 A가 초대 → 계정 B가 참여"를 하려면 커스텀 SMTP부터 붙여야 한다.

→ `signInWithPassword` / `signUp`. 콜백 라우트도, 이메일 템플릿도, SMTP도 필요 없다.
**복잡함의 대부분이 "메일로 링크를 보낸다"는 결정 하나에서 파생됐다는 게 요점이다.**

셋은 배타적이지 않다. 같은 사용자에 대해 비밀번호·매직링크·카카오를 동시에 지원할 수 있으므로
비밀번호로 P1을 뚫고 나머지는 필요할 때 얹는다.

⚠️ **대시보드에서 `Confirm email`을 꺼야 한다.** 켜져 있으면 `signUp`이 세션 없이 사용자만 만들고
확인 메일을 보내 — 결국 SMTP 문제로 되돌아간다. 켜져 있어도 화면이 막다른 길로 끝나지 않게
`check-email` 상태를 남겨 뒀지만, 이 앱의 전제는 꺼져 있는 쪽이다.

### D-037 · 폼 에러는 "귀속 필드가 있는가"로 2계층 분리 (2026-07-31)
기존 로그인 폼은 **모든 서버 에러를 비밀번호 필드에 붙였다.** "이메일을 입력해 주세요."가
비밀번호 칸에 떴고, 더 나쁜 건 `aria-invalid`·`aria-describedby`가 **엉뚱한 입력**에 걸려
스크린리더가 잘못된 필드를 지목한 것이다.

→ `AuthState.field`가 있으면 그 필드에, 없으면 폼 상단 `FormAlert`에 띄운다. 같은 문구를
두 곳에 중복하지 않는다.

**자격 증명 오류에는 `field`를 채우지 않는다.** 어느 쪽이 틀렸는지 알 수 없고, 추측해서
이메일 쪽에 붙이면 **그 주소로 가입된 계정이 있는지가 새어 나간다.** "이미 가입된 이메일"도
마찬가지로 비운다 — 고칠 곳이 입력이 아니라 세그먼티드 컨트롤이다.

**`aria-live`를 쓰지 않는다.** 라이브 리전은 내용이 바뀌기 *전에* DOM에 있어야 읽히는데
에러 `<p>`는 에러와 동시에 마운트돼 상당수 AT에서 침묵한다. 대신 제출 실패 시 해당 입력에
포커스를 옮긴다 — 그러면 `aria-describedby`가 포커스 시점에 확실히 낭독된다. 이게 더 견고하다.

### D-040 · "라벨 — 값" 한 줄을 `DataRow`로 뽑는다 (2026-07-31)

→ `data/data-row.tsx`에 `DataRow`(라벨 `body-sm` 뮤티드 / 값 `money-sm` `.num`)와
`DataRowGroup`(`divided`로 상단 구분선)을 둔다. 값에 **숫자를 넘기면 `MoneyText`로 렌더**해
화면이 `formatWon`을 직접 부를 이유를 없앤다. 차감 항목은 `-1234`가 아니라 `minus` 플래그다 —
음수 값을 넘기면 부호가 포맷터를 타면서 정렬이 흔들린다.

### D-041 · 그림자는 토큰으로 두고, 다크에서는 안쪽 하이라이트로 대신한다 (2026-07-31)

**띄우는 신호를 안쪽 1px 하이라이트가 만들게** 한다. 검정 그림자는 바닥을 누르는 역할만 남는다.

시트, FAB)에만 쓴다 — 카드에까지 그림자를 얹으면 목록 화면이 금방 지저분해진다.

### D-042 · 빈 상태와 경고는 "다음 행동"이 있어야 끝난다 (2026-07-31)

### D-043 · 로딩·에러 골격은 라우트 그룹에 기본값을 두고 화면이 덮어쓴다 (2026-07-31)

### D-044 · `cn()`에 타입 스케일 9단을 등록한다 (2026-07-31) 🔴
tailwind-merge는 자기가 모르는 `text-*`를 **색 클래스로 분류한다.** 그래서 `text-body-sm`과
`text-muted-foreground`가 같은 `cn()`에 들어가면 **뒤의 색이 앞의 크기를 밀어내고 크기가 사라진다.**

```
cn("text-body-sm", "text-muted-foreground")  →  "text-muted-foreground"   ← 13px 소실
```

실제로 8곳이 이미 깨져 있었다 — `WarningBanner` 제목(13→15px) · `StageBadge`(12→15px) ·
`MoneyText muted` · `DataRow` 값 · `EmptyState` 설명 · `ListRow` 예상 제목 · `SectionHeader level="sub"`.
**"화면마다 글자 크기가 반칸씩 다르다"는 진단의 원인이 화면 코드가 아니라 `lib/utils.ts` 한 곳이었다.**

→ `extendTailwindMerge`로 `font-size` 그룹에 9단을 등록한다.
**`globals.css`의 `@theme`에 `--text-*`를 추가하면 이 목록에도 반드시 같이 추가한다.**
안 그러면 새 크기가 조용히 사라지는데, 빌드도 린트도 잡아주지 않는다.

### D-045 · 화면의 결론을 맨 위에 둔다 (2026-07-31)

### D-050 · 동작 없는 행에는 셰브런을 달지 않는다 (2026-07-31)

### D-051 · 예산 카드는 전부 접어 두고, 경고 배너가 펼친다 (2026-07-31)
초과된 대분류 카드를 자동으로 펼쳤더니 소분류가 14행이라 **첫 화면이 2,400px**가 됐다.
나머지 3개 대분류를 보려면 한참 스크롤해야 해서, 이 화면의 목적인 **배분 전체 조망**이 사라진다.

→ 4장 모두 접어 둔다. 문제 카드로 가는 길은 경고 배너의 조치 버튼이 준다 —
**펼치고 · 스크롤하고 · 포커스를 옮긴다.**

- 순수 앵커(`href="#id"`)로는 스크롤만 되고 카드는 접힌 채 남는다.
  반대로 `open` 상태를 페이지로 끌어올리면 카드 목록 전체가 클라이언트 컴포넌트가 된다.
  → 배너 버튼이 `budget:reveal-major` 커스텀 이벤트를 쏘고 카드가 자기 것만 받는다.
- 스크롤만 하고 포커스를 두면 키보드 사용자는 무엇이 열렸는지 알 수 없다.
  포커스는 `preventScroll: true`로 옮기고 이동은 버튼이 맡는다 — 안 그러면 두 번 튄다.
- 최초 해시를 읽어 펼치지 않는다. 효과 안 동기 setState는 연쇄 렌더가 되고
  (`react-hooks/set-state-in-effect`), 초기 상태로 옮기면 SSR과 갈려 하이드레이션이 어긋난다.

### D-052 · 총 가용예산 `0`은 "0원"이 아니라 "아직 정하지 않음"이다 (2026-07-31)
온보딩에서 총 가용예산을 **선택 입력**으로 정했다(제품 오너 결정). 이 시점에 정확한 금액을 아는
사람은 드물고, 기본값을 깔면 홈의 모든 게이지 분모가 **우리가 지어낸 숫자**가 되기 때문이다.

대가로 `total_budget = 0`인 스페이스가 정상적으로 존재한다. 그런데 0은 **미입력**이지 금액이 아니다.

→ 화면은 값을 그대로 렌더하지 않고 `> 0` 여부로 분기한다(`hasTotalBudget`).

- **`₩0`을 `display`(32px)로 띄우지 않는다.** 이 화면에서 가장 강한 요소라 거짓말이 가장 크게 나간다.
  "아직 정하지 않았어요" + 다음 행동(설정 › 예식 정보)을 준다 (D-042).
- **진행률 바를 그리지 않는다.** 분모가 없다. 0으로 나눈 `NaN%`·`Infinity`가 화면에 나가면 안 된다.
- **초과 판정 자체를 건너뛴다.** 기준이 없는데 넘었다고 하면, 배분을 정상적으로 해 둔 사람에게
  "총 예산보다 ₩26,000,000 많아요"라는 헛경고가 뜬다.
- 같은 이유로 `Space.totalBudget`의 타입 주석에 이 규칙을 박아 뒀다. 값만 보고 쓰면 반드시 틀린다.

### D-053 · 목업과 실데이터의 경계는 축이 하나다 (2026-07-31)
P1에서 예식 정보만 실데이터로 넘어가고 원장(예산·지출·하객)은 P2~P5까지 목업으로 남는다.
둘을 어떻게 한 `fixtures.ts` 안에서 공존시킬지가 문제였다 — 여기서 축이 두 개가 되면
(`?fixture=` × 로그인 여부) 조합마다 다른 화면이 나와 아무도 상태를 재현하지 못한다.

→ **`?fixture=`는 원장 스위치다.** 세 세트 전부 **예식 정보는 DB 값으로 덮인다.**
로그인한 사람이 어느 세트를 보든 D-day는 자기 예식일이어야 하기 때문이다.

| 무엇 | 어디서 | 실데이터 전환 |
|---|---|---|
| 예식 정보 (이름·예식일·총 가용예산) | DB `couples` | **지금 (P1)** |
| 원장 (예산·지출·하객·저축) | fixture | P2 · P3 · P5 |

- 화면 코드는 손대지 않는다 — 선택자 함수(`getMockHome()` 등) **본문만** 바뀐다. CLAUDE.md의 데이터 경계 규칙.
- **최소보증인원·평균 축의금·1인 식대는 일부러 덮지 않는다.** 계산식이 P5 소관이라, 지금 덮으면
  목업 명단(207명)과 실제 보증인원이 섞여 **DoD 회귀표의 `13명 부족`이 조용히 틀어진다.**
  원장이 실데이터가 되는 단계에서 같이 넘긴다.
- DoD 회귀표 9개 수치는 전부 원장에서 파생되므로 이 오버레이의 영향을 받지 않는다.
- 스페이스가 없으면(로그아웃·조회 실패·Supabase 미연결) fixture 값이 그대로 남는다 —
  목업만으로 화면을 보던 흐름이 막히지 않는다.

**D-day 기준일도 여기서 갈린다** (→ D-013). 목업 예식일(2026-11-14)에 대해서만 `MOCK_TODAY`로
기준일을 고정해 결정적으로 만들고, 실데이터일 때는 실제 오늘을 쓴다. 이때 서버 로컬 시각
(Vercel = UTC)을 그대로 쓰면 **한국의 오전 9시 이전 사용자에게 D-day가 하루 밀린다.**

### D-054 · `"use client"` 모듈의 함수는 서버 액션이 부를 수 없다 (2026-07-31)
`code-input.tsx`가 초대 코드 정규화·검증 헬퍼(`normalizeInviteCode` · `isInviteCode` ·
`INVITE_CODE_HINT`)를 같이 export한다. 문구와 정규식을 한 곳에 두려던 것인데,
**서버 액션이 이걸 import하면 호출 시점에 터진다** — `"use client"` 모듈의 export는
서버에서 클라이언트 참조 프록시가 되지 순수 함수가 아니다.

→ 코드 **형식 검증을 클라이언트 액션 래퍼로 올렸다.** `useActionState`에 클라이언트 함수를
물리고, 형식이 통과한 코드만 서버 액션으로 내린다.

- 얻은 것: `O`/`0` 오독 같은 형식 오류에 서버 왕복이 사라졌다.
- **잃은 것: 두 폼의 점진적 향상(JS 없이 제출)이다.** 온보딩은 `SegmentedControl`·`AmountInput`
  때문에 어차피 JS가 필요해 감수했다. **로그인 폼은 여전히 순수 Server Action이다** — 그쪽은
  이 대가를 치르지 않았으니 같은 패턴으로 끌고 가지 말 것.
- 다음에 검증 로직을 공유해야 하면 **`"use client"`가 없는 별도 모듈**(`lib/invite-code.ts` 같은)로
  빼는 게 정석이다. 지금은 소비자가 온보딩 하나뿐이라 미뤘다.

### D-055 · 서버 응답에 따라 입력을 비울 때는 `key` 리마운트 (2026-07-31)
`COUPLE_FULL`(이미 두 사람인 스페이스에 참여 시도)에서 초대 코드 필드를 비워야 한다.
`useEffect` + `setState`가 자연스럽지만 **이 저장소는 `react-hooks/set-state-in-effect`가 error다**
(react-compiler 린트). 예산 카드의 해시 딥링크도 같은 규칙에 걸려 포기했다(→ D-051).

→ 서버가 `codeResetToken`을 증가시키고, 화면이 그 값을 `key`로 써서 코드 필드를 **리마운트**한다.

"언제 비우는가"가 서버 응답 하나로 못 박혀서 오히려 더 낫다 — 효과 의존성 배열로 관리하면
"에러가 같은 값으로 두 번 오면 안 비워지는" 종류의 버그가 생긴다.

### D-056 · 온보딩 1→2단계 상태는 쿼리 파라미터로 넘긴다 (2026-07-31)
`couples.wedding_date`가 NOT NULL이라(→ D-028) 예식일·총예산을 받은 뒤에야 `create_couple()`을
부를 수 있다. 그래서 이름·역할(1단계)과 예식 정보(2단계)가 갈린다.

→ `/onboarding/wedding?side=groom&name=…`. **sessionStorage는 서버 컴포넌트가 못 읽는다** —
2단계 페이지가 서버에서 커플 유무로 생성/확인 화면을 갈라야 하므로 URL이어야 한다.

- 새로고침·딥링크·뒤로가기에서 값이 살아남는다.
- 2단계의 뒤로가기는 `router.back()`이 아니라 `href="/onboarding?side=…&name=…"`.
  1단계가 자기 `searchParams`로 초기값을 채워 입력이 복원된다.
- `side`가 없거나 `groom|bride`가 아니면 조용히 `/onboarding`으로. **`name`이 비어도 되돌린다** —
  이 화면에는 이름을 고칠 입력이 없어서, 서버가 `DISPLAY_NAME_REQUIRED`를 돌려주면 막다른 길이 된다.
- 이름은 `maxLength={20}`으로 잘라 URL 길이도 같이 제한한다(DB에는 길이 제약이 없다).

**확인 화면은 멤버 수로 한 번 더 갈린다.** 멤버가 나 혼자면 방금 *만든* 사람이다(홈에서 뒤로가기로
이 주소에 다시 온다). 그때 "예랑으로 참여했어요"는 거짓말이라 "만들었어요"로 바뀐다.

### D-057 · 🔴 오참여는 복구할 수 없다 — `leave_couple()`이 없다 (2026-07-31)
`redeem_invite`는 되돌릴 수 없고, `couple_members_user_unique` 때문에 다른 스페이스로 옮길 수도 없다.
**엉뚱한 코드로 참여하면 계정을 버리는 것 말고 복구 수단이 없다.**

→ P1-3에서는 만들지 않는다. 생성자가 나가면 스페이스가 고아가 되므로 조건 설계가 필요해
즉흥으로 만들 대상이 아니다. 대신 **참여 버튼 위에 "코드를 보낸 사람이 맞는지 확인해 주세요"**를 두어
사전 방지하고, `leave_couple()`을 **P1 백로그 최상단**에 올린다.

⚠️ **이 항목은 D-058로 해소됐다.** 아래를 본다.

### D-058 · 오참여 복구를 연다 — 나가기 · 24시간 축출 · 만료 48시간 (2026-08-01)
D-057을 뒤집는다. `/settings/invite`(코드 발급 화면)를 설계하면서 "한 번 연결되면 뺄 수 없어요"를
경고 문구로 적으려다, **그건 대안이 아니라 회피**라는 것이 분명해졌다. 스키마를 다시 보니
막고 있던 것은 DB 제약이 아니라 **아직 안 만든 함수**였다 — `couple_members`에 DELETE 정책도
GRANT도 없을 뿐, `SECURITY DEFINER` RPC로 열면 그만이다. 데이터도 안 깨진다:
예산·지출·하객은 `couple_id`에 매달려 있고 `expenses.created_by`는 `on delete set null`이라
멤버가 빠져도 원장이 남는다. 나간 사람은 `current_couple_id()`가 null이 되어 RLS가 전부 막는다.

실패를 셋으로 나누고 **둘만 연다**:

| | 상황 | 대책 |
|---|---|---|
| A | 내가 엉뚱한 스페이스에 들어갔다 | `leave_couple()` |
| B | 남이 내 코드로 들어왔다(비협조) | `remove_member()` — 가입 후 **24시간 이내**만 |
| C | 파혼·이별로 영구 축출 | **열지 않는다.** 별도 판단이 필요한 문제다 |

→ `supabase/migrations/0008_membership_recovery.sql`. 판단 네 가지:

**1. 혼자일 땐 나갈 수 없다 — `delete_couple()`로 이름을 가른다.** `couples`에 owner가 없어서
마지막 멤버가 나가면 아무도 접근 못 하는 유령 행이 남는다. 그런데 그 동작의 실제 결과는
"빠지기"가 아니라 **cascade로 전부 지우기**다. 결과가 다르면 버튼 이름도 달라야 한다.
`delete_couple()`은 혼자일 때만 허용한다 — 둘이 쓰는 데이터를 한 사람이 지울 수 있으면 안 된다.

**2. 🔴 나보다 늦게 들어온 사람만 내보낼 수 있다.** 시간 창(24h)만 걸면
**유출된 코드로 들어온 쪽이 24시간 안에 원래 주인을 쫓아낼 수 있다** — 복구 수단이 그대로
공격 수단으로 뒤집힌다. `target.created_at > my.created_at`을 같이 건다. 생성자의 행은
`create_couple()` 시점에 생기므로 참여자는 언제나 나중이고, 따라서 참여자는 생성자를 못 뺀다.

**3. 창을 24시간으로 닫아 두는 것은 C를 막기 위해서다.** 유출은 대개 즉시 알아채고
그 시점엔 데이터도 거의 없다. 창을 무제한으로 열면 이별에 의한 축출이 이 경로로 흘러들고,
그건 "상대의 기록을 지우는" 문제라 훨씬 신중한 설계가 필요하다.

**4. 초대 코드 만료를 7일 → 48시간으로 줄인다.** 코드 엔트로피(32⁶ ≈ 10억)는 문제가 아니다.
문제는 유출이므로 **노출 창을 줄이는 것이 직접적인 대책**이다. 48시간이면 카톡으로 보내고
상대가 다음 날 확인하는 흐름은 그대로 덮는다.

**승인제(참여 요청 → 기존 멤버 승인)는 채택하지 않았다.** 예방으로는 가장 강하지만 알림이
없는 지금 구조에서는 참여자가 "코드를 넣었는데 아무 일도 일어나지 않음" 상태로 방치된다.
2인 앱에 그 복잡도는 과하다. 유출 대응은 사후 24시간 창으로 충분하다고 봤다.

→ `/settings/invite`의 경고 문구가 이 결정에 달려 있다. "뺄 수 없어요"가 더 이상 참이 아니다.

### D-059 · "코드 없음"과 "코드를 못 읽음"을 같은 상태로 만들지 않는다 (2026-08-01)
`active_invite()` 실패를 `null`로 뭉개면 화면은 "지금 쓸 수 있는 코드가 없어요 → [만들기]"를 그리고,
사용자가 그 버튼을 눌러 **살아 있는 코드를 죽인다** — `create_invite()`가 기존 미사용 코드를
폐기하기 때문이다. **조회 실패가 데이터 손실로 번지는 유일한 경로다.**

→ 셀렉터가 `{ status:"ok", invite } | { status:"unavailable" }`로 나눠 돌려준다
(`lib/supabase/invite.ts`). 화면은 `unavailable`일 때 **"없어요"라고 말하지 않고**(있는지 모르는
것이다) `InlineError`를 놓으며, 발급 버튼은 남기되 **확인 시트를 강제**한다.

같은 이유로 `side`를 `Side`로 좁히지 못한 경우도 `unavailable`로 돌린다 — 코드가 있는데
못 읽은 것이므로 "없음"으로 처리하면 역시 멀쩡한 코드가 죽는다.

### D-060 · 초대 코드는 재발급만 확인하고 최초 발급은 확인하지 않는다 (2026-08-01)
재발급은 이미 카톡으로 보낸 코드를 화면에 아무 흔적 없이 죽인다 — 이 화면에서 유일하게
**조용히 망가지는** 동작이다. 최초 발급은 잃을 것이 없어 확인을 붙이면 마찰만 남는다.
**확인 비용은 잃을 것이 있을 때만 낸다.**

→ 확인은 `layout/confirm-sheet.tsx`가 받고, 시트 본문에 **죽을 코드를 문자로 박는다**
("지금 코드 K7X2M9는 즉시 쓸 수 없게 돼요"). 성공 직후 `WarningBanner tone="info"`로
"이전 코드는 더 이상 쓸 수 없어요"를 한 번 더 말한다 — **재발급일 때만**이라 폼이 `had_code=1`을
실어 보내고 서버 액션이 `regenerated`로 돌려준다.

### D-061 · 할 수 없는 동작은 비활성 버튼이 아니라 없는 버튼이다 (2026-08-01)
세 자리에서 같은 판단을 한다 — 두 사람이 이미 연결됐을 때의 코드 발급(`COUPLE_FULL`),
`canRemove`가 거짓인 멤버의 내보내기, 혼자일 때의 나가기.
`disabled` 버튼은 눌러도 아무 일이 없어 D-050의 거짓 어포던스와 같은 문제를 만든다.

→ 버튼을 걷어내고 그 자리에 **이유 한 문장**을 둔다("초대 코드는 더 이상 필요하지 않아요").
나가기/삭제처럼 **결과가 다른 두 동작**은 나란히 놓고 하나를 죽이는 대신 **지금 할 수 있는
하나만** 그린다.

예외는 `ConfirmSheet`의 `acknowledge` 게이트다 — 그건 사용자가 **바로 위에서 열 수 있는**
비활성이라 "아무것도 할 수 없는 비활성"이 아니다. 되돌릴 수 없는 스페이스 삭제에만 붙인다.
남발하면 체크가 습관이 되어 아무것도 막지 못한다.

### D-062 · 복사·공유는 없어도 되는 편의고, 최후 폴백은 사람이 읽는 것이다 (2026-08-01)
`navigator.clipboard`·`navigator.share`는 비-HTTPS·데스크톱·권한 거부에서 통째로 없거나 예외를 던진다.

→ **폴백의 본체는 버튼이 아니라 값이다.** 코드를 타입 스케일 최대치 `text-display`(32px) + `.num` +
`select-all`로 띄워, 전부 실패해도 읽거나 한 번 눌러 선택해 옮길 수 있게 한다.

- 공유는 지원될 때만 렌더한다. 미지원이면 복사가 전폭이 되는데 **둘 다 h-12 한 줄이라 세로 점프가 없다.**
- 능력 감지에 `useEffect` + `setState`를 쓰지 않는다(`set-state-in-effect`가 error).
  `useSyncExternalStore`의 서버 스냅샷(false)/클라이언트 스냅샷이 하이드레이션까지 맞춘다.
- `AbortError`(사용자가 공유 시트를 닫음)는 **실패가 아니다.** 그 밖의 공유 실패는 조용히 복사로 대체한다.

### D-063 · `/settings/*` 하위 화면 셸 — `back` 경로 헤더 + 하단 탭 유지 (2026-08-01)
`/settings/invite`가 첫 하위 화면이라 여기서 굳는 것이 나머지 4개의 규격이 된다.

→ `<AppHeader back="/settings" action={null} title="…" />` + `Screen` + 하단 탭 유지.
**우측은 반드시 비운다** — 기본 액션(설정 아이콘)은 지금 있는 곳으로 가는 링크다.

하단 탭이 있어도 뒤로가기를 뺄 수 없다: iOS PWA에는 하드웨어 뒤로가기가 없고, 딥링크로 들어온
사람에게 올라갈 곳이 화면 안에 있어야 한다. `back`이 history가 아니라 **경로**인 이유도 같다.
라우트마다 자기 `loading.tsx`를 두고 `HeaderSkeleton`에 `back`을 켠다 — 빼면 제목이 44px 튄다.

설정은 자동 저장이 원칙이지만(D-019) **액션 화면(발급·내보내기·삭제)은 명시적 버튼이다.**

### D-064 · 화면 문구에 박히는 상수는 `next/headers`에 닿지 않는 모듈에 둔다 (2026-08-01)
`INVITE_TTL_HOURS`(48)·`REMOVE_WINDOW_HOURS`(24)를 `lib/supabase/{invite,space}.ts`에 뒀더니
**빌드가 깨졌다.** 두 값은 화면 문구에 박히고("48시간 동안 한 번만"), 그 문구 모듈을 클라이언트

→ `src/lib/membership.ts`를 만들어 두 상수만 두고 **아무것도 import하지 않게** 했다.
`lib/supabase/space.ts`도 여기서 받아 쓴다. D-054("`"use client"` 모듈의 함수는 서버 액션이
부를 수 없다 → 별도 모듈로 뺀다")와 같은 처방이 **반대 방향**으로 필요했던 경우다.

🔴 이 값들은 **DB의 사본이지 진실이 아니다.** 바꾸려면 마이그레이션(`0008`)을 같이 고친다.

### O-002 · 최종 손익의 비교 대상 — 결혼식 *예산*인가 *지출*인가
기획안에는 `Σ실제 축의금 − Σ결혼식 지출`로 되어 있으나, 예식 전에는 지출이 아직 안 끝나 손익이
과대하게 잡힌다. 현재 구현은 **예식 전 = 예상 축의금 − 결혼식 예산 합계**, 예식 후 = 실제끼리
비교하는 안으로 그렸다. 보증인원 미달 추가 식대도 손익에 넣었는데 이건 기획안에 없던 항목이다.

### O-004 · Pretendard를 npm 유지할 것인가 self-host로 옮길 것인가
`pretendard@1.3.9`는 모든 포맷을 포함해 `node_modules`가 ~98MB 늘어난다. 배포 번들에는 실제
참조되는 woff2만 들어가 런타임 영향은 없다. 저장소가 부담되면 `public/fonts/`에 variable
dynamic-subset만 복사해 self-host 하는 대안이 있다(복사 스크립트가 하나 늘어남).
→ 현재는 npm 설치 유지. 버전 관리가 되고, 나중에 옮기는 건 언제든 가능하다.
