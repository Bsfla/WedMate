08 / OPEN

구현 전 결정이 필요한 것

시안을 그리면서 플랜만 봐서는 드러나지 않았던 것들입니다. 이 네 가지가 정해지면 바로 구현에 들어갈 수 있습니다.

01
로즈 하나가 세 가지 의미를 갖습니다 — primary · 예신 · 결혼식 #E11D48이 CTA색이자 예신 색이자 결혼식 대분류 색입니다. 결산 화면에서 로즈 막대가 "결혼식"인지 "예신"인지 색만으로는 알 수 없습니다. 시안에서는 라벨 병기로 막아뒀지만, 근본 해결은 둘 중 하나입니다 — (a) 결제자 팔레트를 액센트와 분리(예신 #DB2777 핑크로 이동), 또는 (b) 결제자는 아예 무채색 + 라벨로만 표기하고 색은 대분류 전용으로 예약. (b)를 권합니다 — 결제자는 이미 텍스트로 읽히고, 색 예산을 대분류에 몰아주는 편이 차트가 깔끔합니다.
02
"예상 지출"이 총 지출 숫자에 포함되는가 시안은 확정만 총액으로 잡고 예상은 별도 계열로 뒀습니다(홈의 dual bar, 결산 ①은 확정 기준). 시트의 원래 동작은 예상을 월별 타임라인에만 반영합니다. 다만 예비부부 입장에서 "결국 얼마 나가나"는 확정+예상이라, 홈의 대표 숫자를 어느 쪽으로 둘지는 취향 문제입니다. 지금 시안은 확정을 크게, 예상을 보조로 두었습니다.
03
최종 손익의 비교 대상 — 결혼식 예산인가 지출인가 플랜에는 Σ실제 축의금 − Σ결혼식 지출로 되어 있는데, 예식 전에는 지출이 아직 안 끝나서 손익이 과대하게 잡힙니다. 시안은 예식 전 = 예상 축의금 − 결혼식 예산 합계, 예식 후 = 실제 축의금 − 실제 지출로 자동 전환하는 안을 그렸습니다. 보증인원 미달 추가 식대도 손익에 넣었는데, 이건 플랜에 없던 항목이라 확인이 필요합니다.
04
Pretendard를 npm으로 받을 것인가, 서브셋만 self-host 할 것인가 pretendard@1.3.9 패키지는 모든 포맷을 포함해 node_modules가 ~98MB 늘어납니다. 배포 번들에는 실제 참조되는 woff2만 들어가 런타임 영향은 없지만, 저장소가 부담되면 public/fonts/에 variable dynamic-subset만 복사해 self-host 하는 대안이 있습니다(복사 스크립트가 하나 늘어남). 일단 npm 설치를 권합니다 — 버전 관리가 되고, 나중에 self-host로 옮기는 건 언제든 가능합니다.
이 시안에서 하지 않은 것 — Supabase 연결·인증·실제 CRUD(P1~P5) / 다크 모드 토글(P6, 토큰만 정의) / 스와이프 수정·삭제(P3) / PWA 아이콘 PNG(P6) / 체크리스트·웨딩홀 비교(2차 백로그).
